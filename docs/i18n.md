# Internationalisierung (i18n)

Dieses Dokument beschreibt die i18n-Architektur des Forks **TelegramForwarderGerman**
und die zugrunde liegenden Entscheidungen.

## Ziel

- **Deutsch (`de`)** = Standardsprache
- **Englisch (`en`)** = optional
- **Chinesisch (`zh`)** = Fallback und Quellsprache (Upstream)
- Der Fork soll möglichst **mergefreundlich** zum Upstream
  ([Heavrnl/TelegramForwarder](https://github.com/Heavrnl/TelegramForwarder)) bleiben.
- **Keine** direkten Chinesisch→Deutsch-Ersetzungen im Code: Texte werden durch
  Übersetzungsschlüssel ersetzt, die eigentlichen Texte liegen in `lang/*.json`.

## Komponenten

| Pfad | Zweck |
|------|-------|
| `utils/i18n.py` | Lädt die Sprachdateien und stellt `t(key, **kwargs)` bereit |
| `lang/zh.json` | Quellsprache (1:1 aus dem Upstream-Code extrahiert), Fallback |
| `lang/de.json` | Deutsche Übersetzung (Standard) |
| `lang/en.json` | Englische Übersetzung (optional) |

## Sprachauswahl

Die Sprache wird **global** über die Umgebungsvariable `LANGUAGE` gesetzt
(`.env`):

```env
LANGUAGE=de   # de | en | zh
```

Bewusst **keine** sprachbezogene Datenbankspalte / kein Per-User-Setting –
damit bleiben Datenbank, SQLAlchemy-Modelle und Migrationen unangetastet
(Vorgabe „DB nicht ändern").

## Auflösung & Fallback

`t(key, **kwargs)` löst in dieser Reihenfolge auf:

1. aktive Sprache (`LANGUAGE`, Default `de`)
2. Fallback-Sprache `zh` (garantiert vollständig, da aus dem Code extrahiert)
3. der Schlüsselname selbst (sichtbares Signal für einen fehlenden Schlüssel)

Platzhalter werden über `str.format(**kwargs)` ersetzt. Bei Format-Fehlern wird
der unformatierte Text zurückgegeben (kein Absturz), und es wird geloggt.

```python
from utils.i18n import t

t("cmd.help.text", version=VERSION)
t("common.btn.back")
```

## Schlüssel-Konventionen

- Flache, mit Punkten gegliederte Schlüssel, z. B.
  `cmd.help.text`, `settings.rule.enable_rule.name`, `common.btn.close`.
- Platzhalter mit benannten Feldern: `{version}`, `{source}`, `{target}` …
- Markdown-/HTML-Struktur (`**fett**`, Backticks, `<blockquote>`, `<a href=…>`)
  bleibt in **allen** Sprachdateien identisch erhalten – nur der Text wird übersetzt.
- Alle Sprachdateien haben **denselben Schlüsselsatz** (siehe Prüfung unten).

## Was wird übersetzt – und was nicht

**Übersetzt (Benutzertexte):** Buttons, Menüs, Dialoge, Befehlsantworten,
Hilfetexte, Callback-Hinweise, benutzerseitige Konstanten.

**Nicht übersetzt (bewusst):**

- Kommentare, Docstrings und Log-Meldungen (entwickler-/adminseitig) – bleiben
  in der Originalsprache, um die Anzahl geänderter Zeilen und damit
  Merge-Konflikte mit dem Upstream gering zu halten.
- Unberührte Subsysteme: Docker, Datenbank/SQLAlchemy/SQLite, Telegram-Logik,
  AI, RSS, Scheduler, Business-Logik.
- Graubereich (Scheduler-Ausgaben, Standard-AI-Prompts `DEFAULT_AI_PROMPT` /
  `DEFAULT_SUMMARY_PROMPT`): wird in einer **späteren, separaten Phase** bewertet.

## Mergefreundlichkeit

- Neue Texte liegen ausschließlich in **neuen Dateien** (`lang/`, `utils/i18n.py`)
  → konfliktfrei gegenüber dem Upstream.
- Im bestehenden Code wird **nur das String-Literal** durch einen `t(...)`-Aufruf
  ersetzt. Zeilenstruktur, Reihenfolge und Formatierung bleiben unverändert
  → Konflikte bleiben zeilenlokal und leicht auflösbar.
- Keine Umbenennungen, kein Reformatieren, kein Refactoring über die
  Literal-Ersetzung hinaus.

## Migrationsphasen

0. **Infrastruktur + Pilot** (dieser Stand): `utils/i18n.py`, `lang/`-Gerüst,
   Pilot = Willkommens-/Start-/Hilfetext.
1. Settings-UI (`settings_manager.py`, `button_helpers.py`)
2. Callbacks (`handlers/button/callback/*`)
3. Restliche Befehle (`command_handlers.py`, `prompt_handlers.py`)
4. Filter & Konstanten (benutzerseitige Ausgaben, `constants.py`)
5. Abschluss: `en.json` vervollständigen, Vollständigkeits-Check, Doku

## Vollständigkeit prüfen

Schlüsselgleichheit aller Sprachdateien (sollte `True` ergeben):

```bash
python -c "import json; k=[set(json.load(open(f'lang/{c}.json',encoding='utf-8'))) for c in ['zh','de','en']]; print(k[0]==k[1]==k[2])"
```

Fehlende Schlüssel zur Laufzeit erscheinen als Log-Warnung
(`i18n: fehlender Übersetzungsschlüssel: …`) und fallen auf `zh` zurück.
